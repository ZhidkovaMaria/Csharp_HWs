| Утверждение | Abstract class | Interface | Комментарий |
|---|:---:|---|---|
| Может содержать поля с конкретными значениями | + | − | В абстрактном классе можно хранить обычные поля. В интерфейсе нельзя хранить состояние объекта. |
| Может иметь полноценный конструктор | + | − | Конструктор абстрактного класса вызывается при создании наследника. У интерфейса нет конструктора экземпляра. |
| Один класс может наследовать/реализовывать несколько таких типов | − | + | Наследоваться можно только от одного класса. Интерфейсов можно реализовать несколько. |
| Может содержать реализацию метода по умолчанию | + | + | Абстрактный класс может содержать обычные методы. В интерфейсах с C# 8 тоже есть реализация по умолчанию. |
| Может объявлять свойства без реализации | + | + | Для этого используются абстрактные свойства. В интерфейсе свойства обычно задают только сигнатуру. |
| Может быть использован как тип поля или переменной | + | + | В обоих случаях переменная может ссылаться на объект подходящего класса. Это позволяет работать с разными реализациями одинаково. |
| Может наследовать классы | + | − | Абстрактный класс может наследовать другой класс. Интерфейс наследует только другие интерфейсы. |
| Может содержать приватные методы | + | + | Приватные методы доступны в абстрактных классах. В современных версиях C# они также разрешены в интерфейсах. |

## Дополнительный вопрос

Я бы сделал абстрактный класс `Character`, который реализует `IDamageable`. В нём будут общие для всех персонажей здоровье и метод получения урона. Остальные возможности вынес бы в интерфейсы `IInteractable` и `IHealable`.

Наследование:

- `Character : IDamageable`
- `Player : Character, IInteractable, IHealable`
- `Enemy : Character`
- `NPC : Character, IInteractable`

Абстрактный класс здесь нужен потому, что у всех персонажей есть общие данные и одинаковая базовая логика. Интерфейсы удобнее для отдельных действий, которые есть не у всех. Так `Enemy` не получит ненужный диалог или лечение, а `NPC` не будет лечиться, если это не предусмотрено.
